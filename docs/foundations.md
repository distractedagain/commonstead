# Open-source foundation decisions

Research date: **2026-10-12**. This is a bounded evaluation of public primary sources, not a benchmark or security audit. Links describe upstream projects; they do not mean those projects are installed or integrated into Commonstead.

## Release decision

The first release uses Python 3.12 or later, its standard library, SQLite, and original browser JavaScript/CSS. Core workflows need no Python package download, Node toolchain, subscription, paid API, or AI service. This makes a small, persistent CRM workflow easy to install and inspect on one machine.

This is a **local development and evaluation release**, not an internet production platform or a complete Salesforce replacement. The zero-package choice is a delivery tradeoff, not a claim that custom authentication or HTTP infrastructure is preferable to established frameworks. Python explicitly says that [`http.server` is not recommended for production](https://docs.python.org/3.12/library/http.server.html). A TLS reverse proxy protects transport; it does not establish application security, robust request handling, identity recovery, abuse resistance, or operational readiness.

The immediate maintenance priority after the first workflow is to move request handling and identity infrastructure onto an established framework, carry the authorization tests forward, and add reviewed deployment controls. New portfolio modules must not turn the local HTTP adapter into a growing proprietary-style platform within this project.

## Candidates and decisions

Licenses below apply to the named upstream component. Transitive dependencies, documentation, branding, plugins, container images, and model weights can have different terms. A pinned-version dependency audit is required before adoption.

Deferred from the first local package to keep installation dependency-free. This increases current maintenance burden; keep business rules separate from the HTTP adapter. Django itself does not automatically enforce organization scoping. |

Evaluate a Frappe application against the same CRM acceptance tests before committing to the larger custom-object/workflow milestone. Its site model, tightly integrated UI and operational stack would shape the entire suite. No evidence here establishes that such a port is smaller than a Django migration. |
| [ERPNext](https://github.com/frappe/erpnext) | Broad ERP application including accounting and CRM; [GPL version 3](https://github.com/frappe/erpnext/blob/develop/license.txt). | **Adapter or deployment companion candidate.** Reuse business capabilities through a documented integration when revenue/accounting arrives, instead of independently rebuilding regulated accounting machinery. Not a drop-in foundation for the original first CRM release. No code is imported. |
| [Frappe CRM](https://github.com/frappe/crm) | CRM built on Frappe with lead/deal workflows and optional communications integrations; [AGPL version 3](https://github.com/frappe/crm/blob/develop/LICENSE). | **Alternative distribution or future interoperability candidate.** It is a much broader existing CRM than this release. Choosing an original small core gives control over behavior and installation, at the cost of rebuilding mature features. Copyleft is an obligation to assess, not a reason to call the component unsuitable for free software. |
| [SuiteCRM](https://docs.suitecrm.com/user/) | Accounts, contacts, leads, opportunities, tasks, cases and reports; [AGPL version 3](https://docs.suitecrm.com/admin/licensing/). | **Alternative CRM or adapter candidate.** Adopting its application and data model could accelerate mature sales/service features. Deferred because this release has an original Python core and no validated migration or integration with SuiteCRM. Do not imply that Commonstead already matches its breadth. |
| [Keycloak](https://www.keycloak.org/documentation) | Identity/access management with OIDC and SAML support; [Apache-2.0](https://github.com/keycloak/keycloak). | **Planned optional identity provider.** Prefer OIDC to implementing SSO, MFA, recovery and federation from scratch. Adds a separately operated service; application-level tenant authorization remains Commonstead's responsibility. Not required for local quick-start and not integrated yet. |
| [SQLite](https://www.sqlite.org/whentouse.html) | Embedded transactional database; [public-domain dedication](https://www.sqlite.org/copyright.html). | **Adopted through Python's sqlite3 module.** Fits one host, local disk and modest write concurrency. SQLite permits one writer at a time per database file. The current application has not been qualified for clustered operation or network-mounted database files. |
| [PostgreSQL](https://www.postgresql.org/about/licence/) | Relational server under the PostgreSQL License; supports [row security policies](https://www.postgresql.org/docs/current/ddl-rowsecurity.html). | **Planned production database.** Adds operational work but supports the intended server architecture. Use organization-scoped application queries plus reviewed row security as defense in depth. Superusers, BYPASSRLS roles and usually table owners bypass policies; test with the actual application role. A migration is not implemented. |
| [Celery](https://github.com/celery/celery) | Distributed task queue; [New BSD / BSD-3-Clause core license](https://github.com/celery/celery/blob/main/LICENSE), with separately listed incorporated components. | **Deferred until real background tasks.** Candidate for bounded imports, notifications and scheduled reports. A broker, retries, idempotency and operator visibility must be delivered together. No job queue is claimed in the first release. |
| [Temporal server](https://github.com/temporalio/temporal) | Durable workflows and failure/retry handling; MIT. | **Deferred for long-lived workflows.** Suitable candidate for approvals, orchestration and compensating actions after those requirements exist. Operating another service for synchronous CRUD is premature. SDK and UI licensing must be checked separately. |
| [Ollama](https://github.com/ollama/ollama) / [llama.cpp](https://github.com/ggml-org/llama.cpp) | Local model inference runtimes; both repositories identify MIT licenses. | **Planned optional adapters only.** Neither runtime nor any model is installed, bundled, downloaded or called by the first release. Runtime licensing does not grant rights to every supported model. |

## Path to an internet-ready platform

The following are planned acceptance gates, not completed capabilities:

1. Preserve the CRM API and domain workflow tests while moving HTTP routing, session handling, password lifecycle and CSRF protection to a supported framework. Record the exact supported versions and dependency lock/provenance records. Follow the chosen framework's [deployment checklist](https://docs.djangoproject.com/en/5.2/howto/deployment/checklist/), including a production WSGI/ASGI server.
2. Migrate SQLite to PostgreSQL with repeatable schema/data migrations, rollback or restore procedures, cross-tenant constraints, and tests against the deployed database role. Measure concurrency and resource limits instead of inferring scalability from database choice.
3. Add identity verification, password reset, MFA/SSO, persistent abuse controls, session revocation and administrator recovery. Validate authorization across every module and integration. Have independent security review before using sensitive customer data or opening registration to the internet.
4. Supply TLS, explicit trusted hosts/origins, isolated service credentials, safe proxy configuration, encrypted backups with a restore drill, monitoring, secret rotation and update procedures. A container or HTTPS URL alone does not satisfy these gates.
5. Add jobs and an event/outbox boundary when asynchronous features are implemented; test duplicate delivery, retries, failures and tenant routing before adding external email, messaging or payment effects.

## Local AI and practical costs

Core CRM remains functional with AI disabled. A future adapter must use an operator-selected local endpoint and model, explicit per-organization permissions, bounded context, timeouts, and an observable failure state. Model output is untrusted input; it cannot grant permissions or directly execute business mutations. Public model terms, model digest, quantization, provenance and any redistribution restrictions must be recorded for the selected artifact. **No model is selected, and model-license compatibility is currently unknown.**

There is no verified AI hardware minimum for Commonstead because no adapter has been implemented or benchmarked. Model size, quantization, context length and concurrent requests determine RAM/VRAM needs; [Ollama documents those memory/concurrency relationships](https://docs.ollama.com/faq). A rough calculation such as 7 billion weights at 4 bits being 3.5 GB describes weights only, not a sufficient machine configuration. The future release must publish measured RAM/VRAM, disk use, first-token latency and throughput on named hardware before recommending hardware.

Free software does not make hosting, storage, backups, domains, electricity, administrative time, outbound email, SMS, telephony or inference free. The first release sends no invitations through a paid service; manual invitation delivery can exercise the workflow without email infrastructure. Future integrations must be replaceable and opt-in. Do not auto-provision billable services or claim that third-party free tiers are permanent.

## Limits of this evaluation

The table records official descriptions and published license notices inspected on the research date. It does not establish current vulnerability status, implementation compatibility, operational cost, latest stable versions, or that all third-party notices have been reviewed. Product behavior and performance must be evaluated with pinned versions and repeatable tests before adoption. The first release's actual verification evidence belongs in the capability coverage and release records.
